## 一、什么是 SSE

SSE 全称 **Server-Sent Events（服务器发送事件）**，是一种基于 HTTP、让服务器持续向浏览器推送数据的机制。

普通请求通常在返回结果后结束。SSE 则由浏览器先发起请求，服务器保持响应流打开，有新消息就继续写入，浏览器边接收边处理。

它适合通知、任务进度、实时日志，以及 AI 回答逐段显示等场景。**数据在这条流里从服务器发往客户端**；客户端需要提交操作时，可以另外发送普通 HTTP 请求。

------

## 二、与轮询、WebSocket 的区别

| 方式 | 工作方式 | 适合场景 |
| --- | --- | --- |
| 普通轮询 | 客户端定时请求，有无更新都查询 | 更新频率低，实现简单 |
| 长轮询 | 服务端等到有数据或超时再响应，客户端随后再次请求 | 需要较及时更新，又使用普通请求流程 |
| SSE | 在持续的 HTTP 响应流中发送事件 | 服务端持续推送通知、进度、文本 |
| WebSocket | 建立可持续双向发送消息的连接 | 高频双向交互，如协作编辑、实时游戏 |

轮询的及时性取决于查询间隔；SSE 可以在数据产生后持续推送。SSE 本身传输 UTF-8 文本，JSON 也需要先序列化成文本；WebSocket 支持文本和二进制消息。
------

## 三、消息格式

服务器响应的 `Content-Type` 必须是 **`text/event-stream`**，正文采用 UTF-8。每条消息由若干字段行组成，**以空行结束**，例如：

```text
id: 1
retry: 3000
data: {"progress":50}

```

| 字段 | 含义 |
| --- | --- |
| `data` | 消息内容，多行 data 会用换行符拼接 |
| `event` | 事件名称，不指定时默认为 message |
| `id` | 事件标识，供重连时报告接收位置 |
| `retry` | 重连等待时间，单位毫秒，值为非负整数 |

消息末尾的空行是分隔符，只结束响应而没有空行，最后一条消息可能不会触发。以冒号开头的行属于注释，例如 `: heartbeat`，可以定期发送来减少空闲连接超时。

------

## 四、前端如何接收

浏览器提供原生的 `EventSource`。下面假设 `/api/events` 已经是一个返回 SSE 的服务端接口，并约定任务结束时发送 `event: done`。

```js
const source = new EventSource("/api/events");
source.onmessage = (event) => console.log(event.data);
source.addEventListener("done", () => source.close());
source.onerror = () => console.log("连接异常，状态：", source.readyState);
```

`onmessage` 接收默认的 message 事件；命名事件需要用 `addEventListener` 监听。`event.data` 是字符串，如果约定传 JSON，需要自行解析并处理无效数据。`done` 是这里自定义的事件，**不是 SSE 内置的结束信号**。

------

## 五、自动重连与消息恢复

遇到可恢复的断连，原生 EventSource 会尝试重新连接，服务端可通过 `retry` 调整等待时间。触发 `error` 不一定表示连接永久结束，可以结合 `readyState` 判断：`0` 表示连接中或重连中，`1` 表示已连接，`2` 表示已关闭。

服务端发送过 `id` 后，浏览器重连时会通过 **`Last-Event-ID`** 报告最近记录的事件 ID。但补发哪些消息，需要服务端保存记录并实现恢复逻辑；客户端也可能需要按 ID 去重。

**自动重连不等于消息绝不丢失或重复。** 任务结束或离开页面时，应调用 `close()` 停止连接和重连。单纯让服务端结束当前响应，可能导致客户端再次连接。

------

## 六、实际使用中的注意点

**原生 EventSource 使用 GET，不能直接设置请求体或自定义 Authorization 请求头。** 它可以使用 Cookie 认证；跨域需要服务端正确配置 CORS，携带 Cookie 时还需设置 `withCredentials: true`，并满足浏览器的 Cookie 策略。

**需要 POST 或自定义请求头时，可以用 fetch 读取响应流。** AI 对话中可以先提交问题，再逐段读取服务端结果。若返回的是 SSE 格式，需要自行解析事件；fetch 不会自动提供 EventSource 的事件解析、重连和消息恢复。一次读到的数据块可能包含多条消息，也可能只有半条，不能把每次读取直接当作完整消息。

**后端写入了数据，不代表浏览器立即收到。** 服务端需要及时输出，反向代理的缓冲也可能让消息积攒后才一起到达。排查时可以检查代理缓冲、空闲超时和心跳；HTTP/1.x 下还要留意同域多标签页的连接数量限制。

在 Vue / Nuxt 中，可以在 `onMounted` 建立浏览器端连接，接收数据后更新 `ref`，在 `onUnmounted` 关闭连接，避免组件反复挂载时留下多个连接。

## 总结

**SSE 适合服务端持续推送文本数据。原生 EventSource 提供事件解析与自动重连，消息恢复仍需要服务端配合；使用 fetch 接收 SSE 时，这些逻辑需要自行实现。**
